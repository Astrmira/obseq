# Exact join reuse can be narrower than value freshness

The manifest declares an exact stable-ID pair multiset under ordinary integer equality on eligible left rows (active=1), with NULL never matching. A pinned SQLite GENERATED STORED join key is materialized under one deterministic scalar profile and reopened under an evolved same-name runtime profile. The right row multiset is held fixed. Each right ID belongs to one key. All visible output payloads are deliberately identical, and both versions of the native join emit six rows, yet their exact ID-pair sets are disjoint. Independent Python integer/null logic computes both golden pair sets. Physical database bytes and integrity_check are unchanged during the read-only probe.

**Exact query-scoped reuse guard.** Let B(k) be the set of eligible right IDs with register key k, with B(NULL) empty. An eligible left ID l contributes only pairs (l,r) with r in B(k). Thus replacing its stale key a with current b is observationally unnecessary for this join if and only if B(a)=B(b). Distinct non-null keys have disjoint buckets, so the condition simplifies to exact a=b or both keys being absent from eligible-right support (NULL counts as absent). This is an exact membership sidecar contract, not a statement that all derived values are current. Checking only equal bucket counts is not enough: all three changed matching keys have buckets of size two.

The fixture has one stale eligible key with both buckets empty (ID 14) and a real NULL control (ID 15), both safe for this specific join. A native hybrid query uses the stored values only on certified IDs and the evolved runtime value elsewhere; it reproduces all exact runtime pairs. The guard does not promise a speedup: the demonstration evaluates both keys, and application reuse only helps if precise membership and derivation evidence are already cheaply available. Bind support to the eligible right snapshot and comparison policy; re-evaluate if projecting the key values themselves, adding other predicates, allowing type coercions or choosing a different join contract. No outer-join, streaming-concurrency or performance claim.
