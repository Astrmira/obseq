# Composite inner joins require component-specific null policies

R93 repaired typed singleton SQL equality joins by filtering null keys. A global rule “drop nulls from join columns” fails on held-out mixed-predicate joins. This extension builds 12 asymmetric authored table pairs with duplicate keys, adjacent wide int64 values and null patterns; actual pandas 2.2.3 merge is compared with SQLite and a separately evaluated Python integer/null oracle. Row IDs identify bag occurrences. Run `python3 -IB check.py | cmp - result.json` (replay version information is in result.json).

The contract fixes a conjunction of two column comparisons. Each column independently uses either ordinary SQL equality (=) or null-safe equality (N, SQLite's IS NOT DISTINCT FROM). Materialize all keys as exact nullable Int64 before conversion can collapse adjacent integers. Then discard a row iff any of its **ordinary** equality components is absent; do not discard rows missing only null-safe components. Under this scope the rule is exact: for ordinary components, remaining rows have present keys and native equality applies; for null-safe components, the native join's matching null bucket represents IS NOT DISTINCT FROM. The consumer's conjunction of per-column matches is therefore the declared predicate. This argument is for inner equijoins with nullable int64, not outer joins, collations, floating NaNs, or coercions.

The four policy codes ==, =N, N=, NN give respectively 135, 119, 111 and 71 false pairs with default pandas. Explicit typing alone leaves 64, 48, 40 and 0 false pairs. After typing, dropping nulls indiscriminately creates 0, 16, 24 and 64 missing pairs. Exact typing and the per-component filter eliminate both error types in all 48 authored table/policy cases; correct filtering without correct materialization still fabricates matches. Across five adapters there are 240 real join executions. Counts summarize, but exact row-ID pairs determine conformance.

**Benchmark implication.** Put logical comparison operators in the case manifest, not just physical schema and a global null policy. Score false and missing row-ID pairs independently: a too-strict repair can look safe under precision-only scoring. The paired NaN/NULL-style concerns should not be conflated: no floating inputs here, only one potential implicit binary64 materialization. This is held-out authored coverage, not validation on new engines or real datasets, and makes no performance claim.
