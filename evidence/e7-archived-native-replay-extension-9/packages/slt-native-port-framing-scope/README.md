# E5 SQLLogicTest: exact typed identity is stronger than a flattened render receipt

No locally available canonical SQLite C SQLLogicTest or separate Rust runner was found. The canonical C runner is **not executed**; there was no browser verification handling, mirror construction, download or install. Results below deliberately separate a model of [SQLite's documented SLT rendering](https://www.sqlite.org/sqllogictest/doc/trunk/about.wiki) from an actual second implementation: the already admitted, unmodified [official experimental DuckDB Python SQLLogicTest port](https://github.com/duckdb/duckdb-sqllogictest-python/tree/66b0687fd7b21d22eb8c2216c5e26030dc6a3286) against native DuckDB 1.4.3. These controls supplement, do not change or pool with, the earlier E2/E3 E5 results.

Eight authored exact-identity comparisons use closed generated ordered SELECT VALUES queries. Native DuckDB transport assertions check rows, scalar values and runtime types before any fixture comparator is applied. Fixed declared T/I/R types are preserved across each pair, including typed nullable VARCHAR. Run nosort, rowsort, valuesort (one-row positive controls do not independently measure sort effects), and distinguish plaintext from explicit hashes generated by the unchanged native runner. Expected legality is frozen exact typed value/row identity, **not** an assertion that SLT documentation promises such a contract.

| Changed typed data | Documented ASCII model equal? | Stock DuckDB Python plain | Stock DuckDB Python explicit hash |
|---|---|---|---|
| SQL NULL vs text NULL | yes | accepts | accepts |
| empty text vs text (empty) | yes | accepts | accepts |
| A@B vs literal ASCII tab in A,B | yes | rejects | rejects |
| same two cells but move one embedded newline across the cell boundary | no | NA: embedded delimiter in gold | accepts |
| two distinct nearby DOUBLE values with same documented three-decimal render | yes | accepts | rejects |
| 1.0 vs 1.004, distinct under documented three-decimal render | no | accepts | rejects |
| adjacent BIGINTs above 2^53 | no | rejects | rejects |
| unchanged typed control | yes | accepts | accepts |

The row accounting is unchanged across the three modes: ASCII model 12 false accepts / 24 modes total; port plaintext 12 false accepts / 21 representable modes plus 3 NA; port explicit hash 9 false accepts / 24. This is a deliberately designed challenge set, not a population estimate. The documentation model applies ASCII control replacement, literal sentinels and real printing to three decimals; it is not evidence from C or a Unicode policy. Plaintext tabs in this experiment appear only on candidate SQL side in the control-replacement case; gold around embedded newline is not representable unambiguously in the usual literal line protocol and is intentionally not fed to that arm.

## Native framing counterexample

The ordered rows [text a\nb, text c] and [text a, text b\nc] are different typed two-column rows. In the tested port they both produce the same pre-hash stream b'a\nb\nc\n', and the reported scalar count is two for both. This is independently checked as the exact digest and observed with actual stock gold/candidate hash generation and explicit hash verification under all three modes. It is **not an MD5 cryptographic collision**: identical unframed input arises because raw embedded newlines and separator newlines are not distinguished by this implementation. Also, the particular tested plaintext DOUBLE tolerance accepts a 0.004 delta that the explicit hash rejects; plaintext and hashed comparison do not promise identical observed equivalence in this port.

For an exact typed policy, use a separate typed value protocol (NULL flag, type tag, explicit row width and each payload length, canonical numeric encoding under the intended numeric equality), or a strict admission gate excluding all ambiguous/out-of-scope representations. Neither is attributed to standard SLT. Clearly state intended numeric precision and text sentinel policy; do not infer exact equivalence from matching rendered or hashed outputs alone.
