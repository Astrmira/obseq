# EA&B E3/E5: native SQL bag difference checks equality after coercion

Use three previously SHA-pinned public [COVID-19 TweetIDs released hours](https://publichealth.jmir.org/2020/2/e19273/). Typed original IDs and stable local ordinals are bound into an in-memory DuckDB relation; add one explicitly authored NULL key row. Reuse the already studied source but test a **different detector**: bidirectional native EXCEPT ALL instead of the earlier join and cast collision measurements. The F1 mutant changes only the ID representation to DOUBLE, leaving alignment and count unchanged. Compare exact mathematical ID equality by a Python-integer ties-to-even oracle and separately typed native difference; do not use a FLOAT cast as its own ground truth.

DuckDB 1.4.3 and 2.0.1 both produce empty EXCEPT ALL in both mixed-type directions over the full source. DESCRIBE confirms the bound output ID type is DOUBLE. Yet **10,665 of 22,743 original records change exact integer ID**; comparing mathematically represented numeric values back on an admitted exact-int projection yields 10,665 differences in each direction. This back-lift is valid here only for finite integral representable floats bounded by signed int64, and only exposes the current represented values, not lost original IDs. Never use blanket back-cast as repair. The upstream ID collision count is recorded but not needed for this false pass: reflexive comparison of each original against its own narrowed image erases drift whether or not another key collides.

Three native controls, all without injecting faults into either source input:
- With same exact BIGINT schema, vanilla EXCEPT erases a difference in duplicate multiplicity (zero in both directions), while EXCEPT ALL detects one row each direction. Keep this strong stock baseline **after** admission.
- An exact numeric-value contract may intentionally equate integer 7 and double 7. Type-aware order/normalization is a declared choice, not a generic instruction to reject different schemas.
- Authored STRUCT(id BIGINT) versus STRUCT(id BIGINT, memo VARCHAR=NULL) also yields empty EXCEPT ALL after common schema widening. This is a F5 absent-field-vs-present-NULL blind spot in the SQL comparator itself, not a repeated Parquet ingestion experiment.

**Exact admission.** For a chosen typed data-equivalence relation, a native ALL comparator checks multiplicity after mapping both rows into its common type. It is an exact detector on the admitted domain only if that mapping preserves and reflects the intended row equivalence. Sufficiency: matching common-token multiplicities then matches admitted equivalence classes. Necessity: any two distinct equivalent-after-cast rows give two one-row bags that the comparator accepts against exact typed intent (and any split of an intended row equivalence can falsely reject). Validate pre-bind schema and column alignment, retain explicit nested presence when it is in the contract, and require an injective or explicitly justified quotient mapping before claiming exact equality. If both sides already lost source identity during ingestion, an equal later schema does not restore it.

These are [DuckDB documented set operations](https://duckdb.org/docs/current/sql/query_syntax/setops) and [combination casting](https://duckdb.org/docs/current/sql/data_types/typecasting), not a defect allegation.
