# E5: native Polars comparison under exact cent semantics

An exact money-valued acceptance policy is not the same as generic tolerant float frame equality. This test uses the full admitted generated TPC-H SF10 supplier accounts (100,000 rows, native DuckDB DECIMAL(15,2)). It applies an authored uniform +1 cent counterfactual to one account per comparison. This is a systematic operation on pinned benchmark rows, not observed defects or financial events. The original projected key/cents checksum and typed native source admission are recorded.

[Polars 2.1.0 native assert_frame_equal](https://docs.pola.rs/api/python/stable/reference/api/polars.testing.assert_frame_equal.html) runs with default relative 1e-5 / absolute 1e-8 tolerance on all individual Float64 pairs in both orders. Independently adding a cent in Decimal and rounding the two stored Float64 encodings back to exact cents verifies each remained distinct and each represents its own cent class within this range; no float cast collision explains the result. The decimal control uses the actual Polars Decimal(15,2) dtype and separately checks exact constructed values on both sides.

- Default Float64 accepts 82,002 of 100,000 different-cent comparisons; both directions produce the same decisions. All accepted baselines are at least 1,000.00 in this dataset. None of the 9,006 negative baselines is accepted; the source's negative range stays within magnitude 1,000.00. This is support dependence, not evidence that negative values inherently have different tolerance handling.
- check_exact=True Float64 and default Decimal both reject all 100,000 one-cent differences, and pass the 100 independently selected unchanged controls. Decimal is the direct fit to exact-cent semantics; Float64 exact is validated for these specific distinguishable changes and does not guarantee arbitrary representation or adaptation.
- The controlled positive baseline values 1500.00, 1500.01, and 1500.02 accept both adjacent native approximate pairs but reject the endpoints. Thus approximate acceptance cannot define a partition for a canonical exact hash/grouping key. This does not disallow applications that explicitly request pointwise tolerance.

This result compares documented settings to a distinct exact adapter contract, not a Polars bug, previously observed cast-to-same-value failure, or estimate of production incidence. Counts are source-row perturbations, not independent deployments. No latency measurement, installation, Git change, or raw row export.

Run "sha256sum -c SHA256SUMS" against the portable packet (original frozen adapter digests retained in PREEXECUTION-ORIGINAL.sha256); to replay use DuckDB 1.4.3 and Polars 2.1.0 on the existing SF10 staging file: "python3 -B check.py /path/to/tpch.duckdb | cmp - RESULTS.json".
